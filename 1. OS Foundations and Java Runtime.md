### Day 1 — Processes vs threads
Mental model: 
> A process is a fully isolated virtual computer that the OS creates for running a program.

The process has, from it's own POV, it's own CPU and memory, and can interact with files and the outside world. In reality, the OS orchestrates the simultaneous execution for all processes.

> Program (files on disc) --> OS loads it --> a process

You can have many processes for the same program, e.g. many instances of `chrome`. Each has it's own state. 

When a process is created by the kernel, the kernel records a PCB (process control block):
- PID (process id)
- CPU registers
- Memory map
- File descriptors
- Scheduling info
- Credentials
for it.

The kernel manages the isolation of processes so they don't impact each other.

A process cannot access hardware directly. The kernel stands in between.

#### Processes have...

***...their own virtual memory space***
Every process thinks that its memory starts at 0x00000... 
The OS MMU (memory management unit) translates those virtual addresses into physical RAM. Processes are unaware of the actual physical RAM locations.

***...a stack***
Each process gets a stack. The stack stores local variables, return addresses, saved registers. 

***...a heap***
Dynamic memory lives here.

***...CPU state***
When a process is paused, the kernel saves its CPU registers - from the program perspective, it was never stopped.

***...file descriptor table***
Hashmap of things (terminal, file, pipe, network socket) that you can write to.

***...security credentials***
User id, group id, permissions.

***...environment variables***
E.g. it's parents path, home, user

***...arguments***
./program potato 
argv[0] is "./program"
argv[1] is "potato"

#### UNIX process creation
Parent process `Shell` calls `fork()` creating a nearly identical copy of the current process. The child process then calls `exec` which loads a new executable. Think: `fork` and `exec`.

#### Scheduling
The OS can only run one thread per core at a time. The scheduler switches between them at a given time interval OR whenever a thread blocks.

#### Threads vs processes
- Threads are much lighter as they share everything in the process, except the execution state. 

***Threads share***
- The virtual memory - different threads can modify the same variables instantaneously.
- The heap - this is why synchronisation (mutexes, atomics) are often needed
- Global and static variables
- Shared machine code
- Open files - if one thread opens a file, another thread sees the same file position
- Sockets

***Threads do not share***
- Stack (call stack)
- Local variables
- CPU registers (CPU state)
- Program counter - instruction pointer
- Thread-local created global variables (`thread_local int id`)
- Scheduling state

Mental model
> The process owns resources, the thread owns execution state.

Hence creating threads is so much cheaper than starting new processes.

- Theory: what the OS gives a process (address space, file descriptors, PID); what threads share vs don't (stack per thread, heap shared).
- Java: one JVM = one OS process; threads = OS threads (mostly). `jps`, `jcmd`, Activity Monitor.
- Hands-on: start a Java program, find it in Activity Monitor, count its threads with `jstack`.

### Day 2 - The OS scheduler 

#### The schedulers job
- Case: You have 8 CPUs and 100 runnable threads. The scheduler answers the question "which 8 threads should run now?"
- The scheduler makes this decision and tries to balance responsiveness, fairness, throughput, power consumption and take priority into account.
#### Thread states
A thread can be in 1 of the following states at a time: running, runnable or blocked.
- A blocked (waiting for I/O, stuck in mutex, sleep) thread does NOT consume CPU - the scheduler simply runs something else.

#### How to schedule
##### Cooperative scheduling (old systems approach)
- Rule: a thread keeps running until it gives the CPU up - an infinate loop would freeze the entire system. Nothing else runs.
- Advantage: predictable
- Disadvantage: one buggy program can freeze the entire system
##### Preemptive scheduling (modern OS approach)
- Rule: the kernel can interrupt your thread at almost any time

***Timer interrupts***
- The timer gives a few ms per thread at a time
- time slicing appears simultaneous ("ticking")

***Context switching*** (switches between running threads)
- Not free: kernel must save registers, instruction pointers, stack pointers, SIMD state, scheduler bookkeeping AND restore another thread
- Costs CPU time, cash disruption, branch predictor disruption... too many context switches hurt the performance

***Priorities, priority preemption*** (not all threads are equal)
- If a higher priority thread appears, the scheduler may schedule it in immediately
- Extreme priorities can cause starvation (too many high priority threads, low priority background threads never run)
- Priority can also be temporarily boosted by the OS

#### Sleeping vs Yield 
- `sleep` marks your thread as blocked - the scheduler will schedule another thread to run
- `yield` says "I'm runnable, but if someone else wants priority on CPU, let them go first"

> Thread A yield --> scheduler checks others ---> nobody else running ---> return to thread A

- If you do any CPU work, yield will consume it - sleep will simply not use any CPU until it is ready to - it is good that the thread is blocked!

#### Multiprocessor scheduling
- CPU affinity - ideally, one thread stays on one CPU for cache reasons
- Schedulers also perform load balancing
- Each CPU core has it's own queue


- Theory: preemptive vs cooperative scheduling, time slicing, priorities, why "yield" is rarely what you want.
- Java: `Thread.sleep` vs `Thread.yield` vs blocking I/O — what the scheduler does in each case.
- Hands-on: write a tight loop on N threads; observe with `top -H` how time is split.

### Day 3 - Memory layout: stack and heap

Mental model:
> Stack is the automatic memory for function calls 
> Heap is the dynamic memory that you explicitly allocate

#### Stack
- Active function calls
- Every time a function is called, a new **frame** is pushed
- Each **stack frame** contains: local variables, function parameters, return addresses, saved registers, bookkeeping information
- The stack is extremely fast - the CPU maintains only one stack pointer
- Memory is += or -= the new frame
- Stack allocation is extremely fast

#### Heap 
- The heap stores memory that must outlive a single function call
- If you create a new variable for an integer
	- The pointer (to the heap) lives on the stack
	- The integer lives in the heap
- The keyword `new` requests memory from the dynamic memory allocator
	- allocator finds free heap memory
	- reserves enough bytes
	- constructor runs
	- pointer is returned
- Heap objects stay alive until released - either manually or by smart pointers/garbage collection

Each thread has it's own stack.
The threads share the heap.
#### Java vs Python memory model

Main diff is - **who manages the heap**?
- In C++ it is you
- In Java its the JVM
- in Python, the Python runtime

In heap management - python uses **reference counting** in addition to garbage collection (automatic heap management).

Primitive locals (e.g. x = 5) are kept in stack in java. In python, everything is an object (on heap). This is why **Python has significant memory overhead** when compared to Java. Java uses escape analysis to see if the variable is local and adjusts how it is managed accordingly.

##### Java object header
- Contains metadata 
	- Synchronisation
	- Type information
	- Identity hash code
- This lets the JVM support features like **reflection** and **synchronisation**



### Day 4 - References, sharing and identity
#### References

A reference identifies an object. It is also a value in itself. 

reference value --> object value 

People say "objects are passed by reference" BUT ACTUALLY
```
void greet(Person x) {
  x.sayHello();
}

Person p = new Person("Alice");
greet(p); // This line creates a copy of the reference value of p into x!
```
This implies that if p changes, x does not change. If you would reassign x inside greet, p would not be impacted. **Only the copied reference was reassigned.**

Hence it is actually **"pass by value of the reference"**.

Consider you modify Alice inside greet. You modify the object through the reference. This means that everyone who sees Alice will see the changes.

#### Aliases
In aliasing, two or more references identify the same object.
Modifying the object through either of them is visible in both.

Aliasing is convenient:
```
List<String> names = new ArrayList<>();

process(names);
display(names);
```
No copying of the object value is required - just copying of the reference value: aliasing.
But - it can also cause bugs when not expected!

#### Object mutability

Aliasing is harmless for immutable objects - we know what we get and what to expect. 

Mutable things include: ArrayList, HashMap, Person... sharing them means it changes everywhere.

You can also share objects between threads. The object is still one object in memory.

```
Person p = new Person("antti")

Thread a = new Thread(() -> greet(p));
Thread b = new Thread(() -> greet(p));
```

p, thread a param, thread b param are all copies of the same reference.

#### Identity

Objects may contain identical data but have different identities. They can be equal, but have different identities.

Misconception: b = a copies the object. Actually it just copies the reference.

Mental model: reference is like a note with a room number. Whatever happens in the room can be visible to anyone who knows the number. Aliasing means you share the room number. Changing the reference means you change the room number on your note - nobody elses note changes. 

#### Java

`==` compares references - do they reference the exact same object?
`equals()` compares logical equality - e.g. different objects but same sequence of characters will match

##### Final
Final applies to the reference.
```
final Person p = new Person("alice");
```
This means p can never change it's reference - `p = new Person(..` is not allowed! 

This is also called **"reference stability"**.

BUT

`p.name = "bob"` is perfectly fine. The reference stays the same.
Effectively, if an immutable variable is final, it can never change. But mutable things like lists, maps, objects can.

```
final String name = "mary"; // can never change
final ArrayList names = new ArrayList<>(); // may change inside
```

This is a truly immutable list in Java btw
```
List<String> list = List.of("A", "B");
```

### Day 5 - Statics, singletons and confinement

#### Sharing things

**Global state (Statics)**
```
class Counter {
  static int count = 0;
}

Counter a = new Counter();
Counter b = new Counter();

a.count++;
Print(b.count); // 1

// There is only one instance of count
// Can cause race conditions between threads


class Config {
	static String apiKey = "..."
}

foo(config);
// vs
foo(); // <-- global state hidden dependency
```

Global state creates **hidden dependencies**. 

**Singletons** 
A singleton ensures only one instance exists.

```
class Database {
	private static Database instance = new Database();
	
	public static Database getInstance(){
		return instance
	}
}
```

Singleton does not mean thread safe. Race conditions occur because many threads call the same mutable object.

Singletons often become global state because Database.getInstance is available everywhere. **Singletons are often described as global state with extra steps.**

#### Sharing causes problems
Example: two threads edit the same list. 
> read data --> modify --> write data

The outcome varies depending on scheduling. This is why concurrency bugs are notoriously challenging to reproduce.

#### Strategy: Thread Confinement
Instead of sharing, give each thread it's own data.
Mental model: two chefs using the same bowl causes issues. They each should have their own bowls to work with. This is **confinement**.

Synchronisation has a cost as threads wait and CPU caches have to synchronous.

Design progression:
**Global state >> Singleton >> Dependency injection >> Confinement**

#### Java
`static`, singleton and `ThreadLocal` all answer the same question "who owns this piece of state?"

Mental model: lower ownership is always better. Each game object owns it's own score, until score is set as static - at that point, the class itself becomes the owner, and each object sees the same instance.

**What is The Class**

Many think
`Game.class --> One game`
ACTUALLY
`Game.class --> ClassLoader --> Runtime class object`

Due to independent class loaders, the statics are actually completely independent.
Class loaders are independent like apartments. They provide isolation. 


##### Lazy loading? Misc?

Lazy loading can make use of a holder idiom --> this way loading isn't ran on many threads.

**Hands-on: implement a singleton three ways (eager static, DCL+volatile, holder); explain trade-offs.**
```
// Eager static
class Database {
	private Database() {}

	private static final Database INSTANCE = new Database();
	
	public static Database getInstance() {
		return INSTANCE;
	}
}
// Advantages: simplest implementation. `final` makes sure no mutation happens down the line. 
// Tradeoffs: Eager - object is created instantaneously when Database is initialised. Practically a global with extra steps. Initialization is thread-safe. Race conditions occur if instance is later mutated. Implicit dependency.

// DCL (double checked locking) + volatile - lazy initialisation
class Database {
	private static volatile Database instance;
	
	private Database() {}
	
	public static Database getInstance() {
		Database result = instance;
		
		if (result == null) { // <-- 1st check
			synchronized (Database.class) {
				result = instance;
				if (result == null) { // <-- 2nd check
					result = new Database();
					instance = result;
				}
			}
		}
		return result;
	}
}
// Advantages: lazy initialization. Fast hot path after init. 
// Tradeoffs: holder idiom is just simpler. This is easy to implement incorrectly.

// Holder idiom
class Database {
	private Database() {}
	
	private static class Holder {
		static final Database INSTANCE = new Database();
	}
	
	public static Database getInstance() {
		return Holder.INSTANCE;
	}
}
// Advantages: lazy initialisation, minimal code. No explicit synchronisation.
// Tradeoffs

```
