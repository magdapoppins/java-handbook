### Synchronisation 
Do you have **shared mutable state**? You need to synchronise. Otherwise, don't do it.

Many readers, one writer - use `volatile` (it is not about atomicity but about ordering).
```
private volatile boolean running = true;
```

Many readers and writers on one variable - use a lock (or atomic types).
```
AtomicInteger counter = new AtomicInteger(); 
counter.incrementAndGet(); // These atomic types have their own safe methods
```

Many variables need to change in one unsplittable operation - use a lock
```
private final Object lock = new Object();
```

Case: `ConcurrentHashMap` does not give you safe operations out of the box
```
if (!map.containsKey(key)) { map.put(key, value); } // Nooo nonono
map.putIfAbsent(key, value); // yes!
```

Need to do **IO heavy work**? Note that you need to check the DB connection pool/setup. Virtual threads are cheap and can just wait, but they will fill up memory if they gather indefinitely long.
> Rule of thumb: virtual threads remove thread scarcity, not resource scarcity.
```
ExecutorService pe = Executors.newVirtualThreadPerTaskExecutor();
```

Need to do **basic CPU bound work**? You need a regular ThreadPoolExecutor.
```
ThreadPoolExecutor ve = new ThreadPoolExecutor(  
        2,  // core pool size
        3,  // max pool size
        60, // Excess threads will be terminated if they have been idle for more than this.  
        TimeUnit.SECONDS,  
        // Note: uses a bounded 100 queue but will reject/create backpressure - needs a rejection strategy  
        new ArrayBlockingQueue<>(100),
        new ThreadPoolExecutor.AbortPolicy() // ← rejection policy  
);
```
Here you choose between bounded (`new ArrayBlockingQueue<>(100)`) and unbounded queue. 
- Unbound (latency can grow indefinitely) --> queue grows indefinitely and can cause OOM. Pool size always remains at core pool size. Desired when 
- Bounded (work will not wait for longer than x) --> no oom, but you deal with limits. 

Remember that the mechanism for core vs max pool size is:
Use the core pool **- cannot ->** 
	Queue up **- cannot (queue full) ->** 
		increase pool size **- cannot ->** 
			use rejection policy. 

If you use a bounded queue you will need a rejection policy. The common options are:
- just reject (`new ThreadPoolExecutor.AbortPolicy()`) - caller needs to find ways to throttle
- organic throttle - `new ThreadPoolExecutor.CallerRunsPolicy()` - thread that is submitting to queue does the work, slowing down ingestion to the queue. Seen by caller as latency increase.
