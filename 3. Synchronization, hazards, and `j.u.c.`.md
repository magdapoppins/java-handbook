## Day 11 - Intrinsic locks (`synchronized`)

### Every object in Java has an intrinsic lock 

```
synchronised(someObject) { <protected code> }
```

### The monitor pattern 

Shared mutable state, a lock protecting that state and operations that access the state while holding the lock.

Note that the whole read-and-update operation must be atomic.

synchronised provides mutual exclusion - only one thread at a time executes code guarded by a monitor. 

Not just about preventing simultaneous execution, but also about establishing memory-ordering guarantees - threads seeing any and all other threads writes.

### Reentrancy 

- a method can be synchronized - these are approximately equivalent
```
// Instance synchronised method
public synchronised void increment () {
	count++;
}

public void increment() {
	synchronised(this) {
		count++;
	}
}

Counter a = new Counter();
Counter b = new Counter();

a.increment(); // locks a 
```

### Static synchronised method

```
public static synchronised void resetGlobalCount() {
	globalcount = 0;
}

// approximately equal to 

public static void resetGlobalCount() {
	synchronised(Counter.class) {
		globalcount = 0;
	}
}

// it does not lock any specific Counter instance

```

### Locking on `this`
- Can lead to challenges where external code can hold the monitor e.g.
```
public class FoodContainer {
	private int pebbleDesiliters;
	
	public void fill() {
		synchronised (this) {
			pebbleDesiliters++;
		}
	}
}

// AND

FoodContainer container = new FoodContainer();

synchronised(container) {
	// If we enter here, fill() cannot enter
}
```
-- > prefer using a private lock object
```
public class FoodContainer {
	private final Object lock = new Object(); // outside code cannot reach
	private int pebbleDesiliters;
	
	public void fill() {
		synchronised (lock) {
			pebbleDesiliters++;
		}
	}
}
```

Avoid publicly reachable locks!
ESPECIALLY string literals - unrelated code can sync on exactly same string object

- Hands-on: convert a buggy mutable class to thread-safe using a private lock.

## Day 12 - Explicit locks: `ReentrantLock`, `ReadWriteLock`

### Intrinsic locks 

```
synchronised(myLock) {...}
```
An intrinsic lock is automatically acquired on entry and automatically released on exit/error.
It is also reentrant - a thread can re-enter a lock it already holds.

For ordinary mutual exclusion, synchronised is usually the best - it is concise and difficult to misuse.

Explicit locks adds capabilities to these.

### ReentrantLock
An explicitly managed, reentrant mutex.
```
private final ReentrantLock lock = new ReentrantLock();

public void update() {
	lock.lock();
	try {...} // protected state
	finally {
		lock.unlock();
	}
}

```

### When explicit locks beat `synchronized`
#### A. Thread should not wait indefinitely
```
if (java.tryLock(200, TimeUnit.MILLISECONDS)) {
	try {
		performOptimalWork();
	}
	finally {
		lock.unlock();
	}
} else {
	useFallback();
}
```

#### B. Interruptable acquisition
Task cancellation. Graceful shutdown.

```
public void process() throws InterruptedException {
	lock.lockInterruptibly();
	
	try {
		processSharedState();
	} finally {
		lock.unlock();
	}
}

```

#### C. Fair locking - longest waiting thread gets first turn
`private final Lock lock = new ReentrantLock(true);`
This makes it fair.

### ReadWriteLock 

There is also a dual mode read-write lock that can be divided into 
- read mode: several can hold concurrently
- write mode: no other readers or writers may hold

## Day 13 - Deadlock

Thread A holds lock1 and waits for lock2.
Thread B holds lock2 and waits for lock1.
### Coffman conditions
A deadlock can occur when all four Coffman conditions hold simultaneously.

1. Mutual exclusion - one or more resources can be used by only one thread at a time. E.g. 
2. Hold-and-wait - a thread holds one resource while waiting for another - waiting while a lock is already acquired.
3. No preemption - a lock cannot be forcibly removed from it's current owner. The case of e.g. regular synchronized 
4. Circular wait - A waits for something B holds while B waits for something A holds.
Java convention to break these is with clear lock ordering - no circular wait!
### Prevention, avoidance, detection
Prevent: always make sure at least one Coffman condition does not hold.
Avoid: attempt acquisition with tryLock, back off when it fails. Retry later.
Detect: Monitor threads that make no progress - eg through jstack. Recover by restart or cancelling work.

### Java lock ordering: deterministic ordering

This is a problem:
```
public void transfer(Account to, Account from, long amount) {
	synchronized(from) {
		synchronized(to) {
			from.withdraw(amount);
			to.deposit(amount);
		}
	}
}

// Thread 1: transfer(accountA, accountB, 100)
// Thread 2: transfer(accountB, accountA, 50)
```

Assign a lockable object to a stable ordering key - a circular wait cannot form!
```
public void transfer(Account to, Account from, long amount) {
	Account first;
	Account second;
	
	if (from.id() < to.id()) {
		first = from;
		second = to;
	} else {
		first = to;
		second = from;
	}
	
	synchronized(first) {
		synchronized(second) {
			from.withdraw(amount);
			to.deposit(amount);
		}
	}
}

```

## Day 14 - Livelock and Starvation

Both of them are concurrency failures where threads remain active/runnable but no useful progress happens.

*Deadlock* - threads permanently wait for each other - threads not active
"Two people block each other at a doorway and cannot move"

*Livelock* - threads continually react and retry - threads active
Both people repeatedly step aside in the same direction.

*Starvation* - one thread rarely or never gets a needed resource - threads possibly active.
Everyone else keeps getting through, one person never gets their turn.

### Livelock
- Fix: add randomized backoff to e.g. trying to acquire a lock. This will break synchronized retries.
- Fix: use bounded exponential backoff - reduces contention and prevents unbounded spinning.
- Fix: establish a global lock order.

### Retry storms
- Bad pattern: retry immediately if e.g. timeout - retry storm brewing
- Better: add exponential backoff, circuit breakers, retry budgets or rate limiting.

### Starvation
- Example: lock starvation. Many threads simultaneously acquire the non-fair lock. If fairness is not enabled, the threads can bargain for the lock - it can improve throughput because the thread already running can acquire the lock first, but under heavy contention it may lead to starvation.

### Fair and unfair `ReentrantLock`
`ReentrantLock lock = new ReentrantLock(true);` (true is for Fair=true)

It does not guarantee fairness, but can help when guarding against e.g. long tail latency or demonstratable starvation.

### Signals
High CPU, no work done - livelock
Repeated restarts - livelock
Logs show recurring state transitions - livelock

Severe tail latencies - starvation
Lock wait times are extremely uneven - starvation
Some operations complete normally, others wait excessively - starvation

Look at: restart rate, lock acquisition wait time, p99 latency, executor active thread metrics
