### Day 6 — A Thread is a Functon: Java Threading Basics
- an independent path of execution for a program

**Mental model**
- program is a chain restaurant
- process is one restaurant location
- thread is one worker at the restaurant (share the same kitchen, memory)

#### Thread lifecycle

> NEW -> start() -> runnable - blocked/waiting/timed_waiting - runnable -> finishes -> TERMINATED

**1. NEW**
```
Thread t = new Thread(() -> {
	System.out.println("Running");
})
```
Object exists but hasn't been started

**2. RUNNABLE**

```
t.start();
```
Now the JVM schedules the thread. The thread becomes runnable. It is ready to run and is waiting for CPU time. 

Runnable threads: main thread, thread a, thread b - the kernel scheduler switches rapidly between them.

**3. BLOCKED**
Thread is waiting to acquire a monitor lock (synchronized).

```
synchronized(lock) {
	// Only one thread allowed 
}
```
E.g. thread A has the lock. Thread B also tries to enter. It needs to wait for A to exit the synchronized block.

```
Object lock = new Object();

Thread t1 = new Thread(() -> ...) // uses lock
Thread t2 = new Thread(() -> ...) // also uses lock
```

**4. WAITING**
Thread waits indefinitely for other thread to complete. Happens in e.g. `object.wait()`.

```
// or 
worker.start();
worker.join(); // Main thread waits here indefinitely 
```

**5. TIMED_WAITING**
Like waiting, but with a timeout. E.g. `thread.sleep(1000);` or `join(5000);`.

**6. TERMINATED**
- When run() finishes
- A terminated thread cannot be restarted (`IllegalThreadStateException`)!

#### Java
##### Thread
Thread represent a thread of execution. Creating a Thread object creates an object that the JVM can schedule to run concurrently.

Main thread                                         Worker thread 
creates Thread
calls start() -----------------------> run() executes // new thread is actually created here
continues immediately

##### Runnable
Runnable is a functional interface describing a **task**, not a thread. 

>Task = what should be done?
>Thread = who executes it?

It makes sense to separate the work from the thread that performs the work!

```
Runnable printer = () -> {
	System.out.println("hello");
};

Thread t1 = new Thread(printer).start();
```

##### Callable
Runnable cannot return a value (e.g. result, exception), it only ever returns void!
Callable can.

```
// Integer call() throws Exception;

Callable<Integer> task = () -> {
	return 42;
};

Integer result = task.call();
```

##### Daemon threads 
Java has 2 kinds of threads: user threads (normal application threads) and daemon threads (background threads such as garbage collection).

If the only alive threads are daemon threads, the program exits.

`t.setDaemon(true); // do background work`

Daemon threads are good for logging, monitoring, metrics collection...

##### Uncaught exception handlers
- if a thread throws an exception that nobody catches, the thread terminates. (RuntimeException)

```
// You can set an uncaught exception handler that can be useful for e.g. centralised logging, alerting or graceful recovery

Thread t = new Thread(...);

t.setUncaughtExceptionHandler((thread, exception) -> {
	System.out.println("Failure", thread, exception);	
})

// can also be done centrally through

Thread.setUncaughtExceptionHandler(...)
```

### Day 7 - Concurrency is Hard: Visibility and Reordering

Modern CPU optimisations lead to the counterintuitive situation where not all threads see the same sequence of events.

> Visibility - when does one CPU core actually see another cores writes?
> Reordering - operations may happen in a different order than they appear in the source code

```

Core 1                                          Core 2
Thread A                                        Thread B
Registers                                       Registers
L1 Cache                                        L1 Cache
               \                          /
                      Shared memory

```

BUT CPU does not immediately update memory.
RAM is incredibly slow.

Register (1 cycle) vs L1 cache (4 cycles) vs main memory (100-300 cycles)!

#### CPU caches
- Each core has it's own cache
- The caches are pushed to the main memory - with a tiny delay.

**Cache coherence**
Modern CPUs implement cache coherence protocols (eg MESI).
The goal is that **eventually** all cores agree.

#### Store buffers
When code executes, it is actually not even directly written to the cache. 

CPU --> Store Buffer --> Cache --> Memory 

The CPU simply enqueues the data to the store buffer and continues execution immediately. When the store buffer is flushed, the update propagates further.

Store buffer flushes do not necessarily update in order! Meaning: a different thread might see some variables updated and some not.

#### Compiler reordering 

A compiler can reorder operations if it doesn't change the behavior of a single threaded program.
However the change may be seen in another thread.

#### CPU reordering 

Store and commit may be shuffled around in execution. The CPU only has to preserve the guarantees required by it's memory model.

#### The key memory model ideas
- x86-64 (TSO) - relatively strong ordering, some reorderings are still possible (store->load via buffers)
- ARM and RISC-V - weaker ordering, unless explicit synchronisation is used
The OS memory model defines ordering on a stricter level, above language guarantees.

#### Summary
- Multiple threads don't necessarily share instantaneously updated memory!
- CPU caches happen
- Store buffers sit before cache update
- cache coherence protocols synchronise caches eventually
- compilers and CPUs may reorder instructions as long as it doesnt affect the behaviour of a single threaded program

#### Java: the canonical "stop flag never seen" example. Read JCIP §3.1.

Case example - intention
```
main thread                        worker thread 
start worker                       read stopRequested == false 
                                   keep working 
stopRequested = true 
                                   read stopRequested == true 
                                   exit loop
```

**Without explicit synchronisation**, there is no guarantee that a thread will observe anothers write. 
Reasoning in the JIT compiler "in this thread, nothing modifies this variable" - the read can be hoisted outside of e.g. a loop!

Fix: `private static boolean stopRequested = false;` >> `private static **volatile** boolean stopRequested = false;`

```
public final class StopNotSeen {

	private static volatile boolean stopRequested = false;

	public static void main(String[] args) throws InterruptedException {
	
		Thread worker = new Thread(() -> {
			long iterations = 0;
	
			while (!stopRequested) {
				iterations++;
			}
	
			System.out.println("iterations: " + iterations);
		});
	
		worker.start();
		Thread.sleep(1000);
		stopRequested = true;
		worker.join();
	}
}
```

### Day 8 - Java Memory Model: happens-before

> Java Memory Model JMM defines when writes in one thread become visible to another thread - inter-thread memory management as well as allowed JVM and CPU reordering.

These rules must exist to guarantee that multithreaded programs run predictably while modern compilers and CPUs heavily try to optimize code.

The JMM defines 
- when writes become visible
- what reorderings are legal
- when synchronisation is needed to guarantee consistency

> An action in the JMM is something to observe by the memory model, e.g. reading a variable, locking a monitor, finishing a thread...

#### JLS §17.4: Three important orders 
##### 1. Program order
Inside a single thread, actions appear in source code order.
This only applies within a single thread.
##### 2. Synchronisation order
Synchronisation actions 
- monitor lock/unlock
- volatile read/write
- thread start
- thread join
- interrupt
- class initialisation
Have a global order: a single total order that all threads agree upon.
##### 3. Happens-before order
A happens-before edge combines visibility + ordering!

A -- happens before --> B

A's effects are visible to B.
B cannot observe memory before A.

Happens before guarantees program order (in a single thread!)
Happens before follows synchronisation laws.

```
// Case 1 - thread join
class Example {
	static int value;
	
	public static void main() {
		Thread t  = new Thread(() => {
			value = 100;
		})
		
		t.start();
		t.join();
		
		System.out.println(value);
	}
}
// LAW: last action in thread --- happens-before --> thread.join

// Case 2 - volatile
class Example {
	int value;
	volatile boolean ready;
	
	void writer() {
		value = 42;
		ready = true;
	}
	
	void reader() {
		if (ready) {
			System.out.println(value);
		}
	}
}
Example ex = new Example();
Thread writer = new Thread(() -> {
	ex.writer();
})
Thread reader = new Thread(() -> {
	ex.reader();
})
writer.start();
reader.start();

// LAW: volatile write -- happens-before --> volatile read
// Because value = 42 before ready is set, it MUST also observe it because 
// it is part of the visibility state.
// volatile means "publish everything before this"
```

### Day 9 - `volatile`, `final`, safe publication

Each thread has 
- working memory (CPU registars, cache) - local copies of variables
- main memory (heap) - shared by all threads

Without synchronisation, threads are allowed to cache values, reorder instructions and delay writes.

JMM defines the **happens-before** relationship, which specifies when a thread can observe another threads actions.

#### Volatile

Rule 1: "Every read must come from main memory"
Rule 2: "Every write must immediately become visible to other threads"

*Visibility and ordering*

- Volatile does not solve the problem of race conditions since any increment is **read -> update -> write** 
- For race conditions use synchronised or lock or atomic...

Volatile is great for when many threads read but only one thread writes (stop flag, status flag, reference publication aka config passing)...

#### Final

- Cannot be reassigned
- Guaranteed visibility to all threads **after construction**

#### Safe publication

- "Publishing" means making visible to another thread

**You can achieve this by**
- Static initializer (`static final Config CONFIG = new Config();`)
- Volatile reference (`volatile Config config; config = new Config();`)
- Synchronisation (`synchronized(lock) { obj = new Config();};`)
- Final field 
- Concurrent collections (`ConcurrentHashMap, BlockingQueue, CopyOnWriteArrayList`)

#### Double-checked locking (DCL)
```
class Singleton {
	private static volatile Singleton instance; 
	
	static Singleton getInstance() {
		
		if (instance == null) {	
			synchronized (Singleton.class) {
				
				if (instance == null) {
					instance = new Singleton();
				}
			}
		}
		
		return instance;
	}
}
```

#### Better singleton options: Init on demand holder
Lazy, thread-safe, lock-free after init, simpler than DCL.

```
class Singleton {
	private Singleton() {}
	
	private static class Holder {
		
		static final Singleton INSTANCE = new Singleton();
	}
	
	static Singleton getInstance() {
		
		return Holder.INSTANCE;
	}
}

```

- Hands-on: build a thread-safe immutable value object; publish it via a volatile reference.

### Day 10 - Atomicity and race conditions

#### When do race conditions happen
- multiple threads share the same state
- at least one thread modifies it 
- the outcome depends on the "race" between threads

Example
```
int counter = 0;

// two threads both do 
counter++;

// result can be 1 or 2
```
#### Atomicity - atomic vs composite
- An operation that is complete and indivisive with no thread observing an intermediate state
- Example: on/off switch
- Example of non-atomic: assemble furniture step by step
#### Read-modify-write hazards
- Update is usually read-modify-write
- The gap between read and write is what makes it prone to race conditions - it may have observed a previous state
- Can lead to "lost update"!
#### Compare-and-set (CAS)
- Only change the value if nobody else changed it
```
CAS(location, expected, newvalue)
// If location == expected, replace to newvalue
```
This is a lock-free approach to read-modify-write.
You can also use it in a loop: try until succeeds.
#### AtomicInteger, AtomicReference
- both have `.compareAndSet`
#### ABA problem
- CAS does not detect an intermediate change e.g.
`A --> B --> A`
Could cause problems if the state (eg stack) is important.
Use AtomicStampedReference for reference with version!
Could be e.g. a problem in memory allocation when history (has this memory been unused?) matters.

- Hands-on: implement a non-blocking counter with a CAS retry loop; compare against `synchronized`.

```
public class Example {

private static AtomicInteger atomicInteger = new AtomicInteger(0);

public static void main(String[] args) {

while (true) {

int value = atomicInteger.get();

int newValue = value + 1;

updated = atomicInteger.compareAndSet(value, newValue);

if (updated) {

break;

}

}

}

}
```
