## Day 16 - Thread pools

Case: you have a ThreadPoolExecutor with 8 worker threads.
### Overload and backpressure
What should happen if the incoming requests > capacity to process?

- Queue excess work
- Reject it
- Slow down the producer
- Add processing capacity 
- Crash after consuming all resources

1-4 are the good options that a good executor lets you choose from.

#### Unbounded queue 
Workers full --> queue up with no limits. E.g. `new LinkedBlockingQueue<>()`
Will eventually drive you out of memory if processing cannot keep up.
Also will lead to high processing latency.

Another maybe surprising effect is that since the excess is immediately queued, the pool stays at the core pool size instead of growing towards the maximum pool size. This is because the queue will never become full.
```
new ThreadPoolExecutor( 
	4, // corePoolSize
	100, // maximumPoolSize
	60, 
	TimeUnit.SECONDS, 
	new LinkedBlockingQueue<>() 
);
```

### Bounded queue
Eg `new ArrayBlockingQueue<>()` - the system now has an explicit limit 8 worker threads + 1000 queued tasks.
The executor now needs a rejection policy. This is usually good because overload becomes visible: 

- normal load: workers + small queue
- high load: workers + queue filling
- overload: queue full - reject/backpressure

```
new ThreadPoolExecutor( 
	4, // corePoolSize
	100, // maximumPoolSize
	60, 
	TimeUnit.SECONDS, 
	new ArrayBlockingQueue<>() 
);
```

This will give you more predictable memory usage, bounded queueing latency an explicit overload signal.

### ThreadPoolExecutor under the hood

Given corePoolSize = 4, maximumPoolSize = 10, queueCapacity = 100.

When `execute(task)` is called, 

1. Is worker count < core pool size: 
	-  if yes, create a thread and run task
2. if no, can task enter queue? **<-- note that queue is filled before expanding beyond the core pool!**
	- if yes, enqueue
3. if no, is worker count < maximumPoolSize?
	- if yes, create additional thread
4. if no, reject task

### Executor.newCachedThreadPool()
- this is roughly equivalent to a threadpool with unlimited maximum threads and a queue capacity of 0
- threads aren't free --> can lead to classic **resource exhaustion failure**
- use this approach only for very short lived tasks or bursts where concurrency is extremely bounded

### Pool sizing: CPU bound work
- Compute heavy work such as compression, image transformations, simulation, parsing...
- if you have N available CPU cores, pool size N is usually a good starting point, or sometimes N + 1 
- on an 8 core machine, `Executor.newFixedThreadPool(8)`
- Reasoning: only 8 can execute simulateneously anyway, and there is no waiting in the work
- Having more than 8 --> OS has to switch between them, leading to more overhead and worse throughput 

> For CPU heavy tasks, think cores --> threads.

### Pool sizing: I/O bound work
- I/O bound tasks can spend much of their lifetimes waiting 

**More like threads = cores x (1 + waittime / computetime)**

Cores: 8
Wait time: 90ms
Compute time: 10ms

8 x (1 + 90/10) = 80 threads as a starting estimate 

You need to size the pool around the bottleneck you want to protect - be it CPU, memory, HTTP connection limits, latency targets, downstream service capacity...

`.execute()` relies on the threads uncaugh-exception mechanism whereas tasks using `.submit()` have their own exceptions captured in the Future returned.

- Theory: bounded vs unbounded queues, why `Executors.newCachedThreadPool()` is dangerous; pool sizing for CPU-bound vs I/O-bound work.
- Java: `ThreadPoolExecutor` constructor parameters in detail; rejection policies; `ScheduledThreadPoolExecutor`.
- Hands-on: configure a `ThreadPoolExecutor` for a CPU-bound workload and an I/O-bound workload; measure throughput and queue depth.

## Day 18 - Concurrent collections

Concurrent collections are designed for correctness and performance when multiple threads access them at the same time.
### Lock striping 
Instead of locking the entire map (hash table), lock a region containing the modified tea. 

- Theory: lock striping, copy-on-write, snapshot iterators.
- Java: `ConcurrentHashMap` (high-level internals), `CopyOnWriteArrayList`, `BlockingQueue` variants.
- Hands-on: replace a `synchronized` Map wrapper with `ConcurrentHashMap`; verify atomicity of `compute` / `merge` / `computeIfAbsent`.

### Copy-on-write 
Reads are cheap, writes are expensive. On write, create a new copy to read from.

### Snapshot iterators
While using `new ArrayList<>()` you can get `ConcurrentModificationException` - the array has been modified by another thread while another is iterating it.

`new CopyOnWriteArrayList<>()` gives you a snapshot iterator.
Sees the array as it was when it was created. 

### ConcurrentHashMap
Problem: you want to have `.put(key, 1)` in a thread safe way.

For simple counting, `.merge` is recommended over `compute`


### Summary 

thread safe individual operations != atomic compound operations  - read and write can be thread safe, but not atomic!

Concurrent collection encode concurrency patterns in theis APIs.

## Day 19 - Thread-based, not I/O-based server shape

>I/O based servers organize work around sockets. 
>Thread based servers organize work around sessions.

### Reactor/event-loop vs thread-per-session

Classic reactor server
socket A ---
socket B ----------> event loop --> dispatch callback/task
socket C ---

A becomes readable, loop runs As handler, and so on. This works well when the dominant problem is I/O mostly-idle connections - HTTP proxies, gateways, chat fanout...

Problem is that if any of these are blocking and monopolises the loop thread, every other session assigned to that loop stalls.

A thread-orientated server can instead give one "lane" to one session.
### Why thread per session based maps well to long lived sessions

In highly asynchronous systems, order is preserved by ordering deliberately. Otherwise workers may do work in a different order.

> thread-based and actor/session models are conceptually close

### Aren't threads expensive?
1. memory cost - Java thread has a native stack and bookkeeping, tens-hundreds of K of threads are undesirable
2. scheduling/context switching cost - if runnable threads > cpu cores it will force context switching which costs CPU and slows down because of lost cache benefits

Event driven designs such as queues, futures, callbacks etc have their own complexity cost.
